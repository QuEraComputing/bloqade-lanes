### Proposal: absorb the pending Z frame into STAR-X's axis instead of draining it

**Problem.** `EliminateRz`'s `StarRx` handler calls `_drain`, which re-emits the **whole program's** pending frame as native `Rz` before the gadget. Those `Rz` lower to `move.LocalRz` / `GlobalRz`, which the backend can't execute (see `2026-09-14-rz-elimination-design.md`). This happens even with `no_raise=False`. `StarRxRzGateValidation` isn't in `LogicalPipeline`, so nothing in lanes stops it. Reproduced on `8af089e` with `LogicalPipeline(transversal_rewrite=True)`:

| kernel | physical Rz emitted |
|---|---|
| `s(q0); star_rx(q0)` | `GlobalRz` |
| `x(q0); x(q1); s(q0); star_rx([q1]); x(q0)` | `LocalRz` on q0's 7 atoms (q0 isn't touched by the `StarRx`) |
| same, with `star_rx` replaced by `x(q1)` | none (`S` absorbed into q0's next `R`, axis 0.75) |

**Why absorption is exact.** After transversal lowering, STAR-X is `LocalR(0, θ*)` on its 3 support atoms. A pending frame `α` would drain to a transversal `Rz(α)` on all 7 atoms. The identity `EliminateRz` already uses for `R` (angles in turns) then gives, on each atom:

```
LocalR_supp(φ, θ*) · Rz⊗7(α) = Rz⊗7(α) · LocalR_supp(φ − α, θ*)
```

Non-support atoms see no gate, so they commute trivially. So the gadget can take axis `φ − α` and the frame can stay pending, exactly as with `R`. No `Rz` is emitted.

**Proposed change: give `place.StarRx` and `move.StarRx` an `axis_angle` operand.**

- `place.StarRx` / `move.StarRx`: add `axis_angle: ir.SSAValue = info.argument(type=types.Float)`, ordered like `R` (axis then rotation).
- `RewriteStarRx`: emit `move.LocalR(state, node.axis_angle, theta_star, ...)` instead of the hard-coded `py.Constant(0.0)`.
- Carry the axis through `circuit2place.rewrite_StarRx`, `place2move`, and the `MergePlacementRegions` / `MergeStaticPlacement` copies.
- `fuse_gates.StarRxGroup.can_extend` and `reorder_static_placement._group_key`: require/include `axis_angle` identity, so gates with different axes aren't merged.
- Visualizers: report `("axis_angle", "rotation_angle")` for `move.StarRx`, like `LocalR`.

**Native layer.** `EliminateRz` runs before place lowering, so it needs a native-level carrier for the shifted axis. To keep the user-facing `extensions.StarRx` / `star_rx(theta, qubits, qubit_indices)` unchanged:

- add an internal, non-lowerable statement (e.g. `extensions.stmts.StarRxAxis`, with no `FromPythonCall` and no wrapper) carrying `axis_angle`;
- have `EliminateRz` replace each `StarRx` it meets with `StarRxAxis(axis=0 − frame)`. As in the `R` handler, split into one statement per frame group when the qubits' frames differ. Leave the frame pending; don't drain;
- register `StarRxAxis` in `EliminateRz`, in `NormalizeGateAxisAngles` (currently `R`-only), and in `RewritePlaceOperations`. Plain `StarRx` lowers with a constant 0 axis; `StarRxAxis` uses its own.

(Alternative: put `axis_angle` on `extensions.StarRx` itself, with the `star_rx` wrapper supplying 0. That's simpler, but it changes the public statement.)

**Consequences.**
- `S`/`Z`/`H`/`Rz` anywhere in the program compile without emitting any `Rz`. `StarRxRzGateValidation` becomes a policy choice rather than a correctness guard, so it could be dropped or kept as opt-in.
- The `EliminateRz` class docstring goes back to having just the one documented leftover `Rz` (`StarRz`'s).
- Note: a shifted STAR-X isn't a "logical STAR-X about axis −α" in any code-level sense. It's the physical gadget equivalent to drain-then-gadget, and that's all the compiler promises.
